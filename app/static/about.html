    About EmailAssist

    Drop an email thread in, get back a summary, the action items, and one clear next step. Everything it finds collects into a single task list across every thread you have analysed. It runs entirely on this machine — you can unplug the network and it still works.

    Two ways to look at it

    Workspace — one thread at a time

    Drop in an exported .eml thread and get the summary, what to do next, the action items, and the facts a program checked rather than the model recalled — including anything that did not check out. Past analyses stay in the sidebar and reopen exactly as they were.

    Tasks — everything you owe

    One thread answers "what does this need?". The Tasks page answers the question you actually have: what you owe across all of them, and what is late. Every action item from every analysed thread, grouped overdue / today / this week / later, filtered to the ones you own, each linking back to the thread that justifies it. Ticking one is saved locally and looks the same from either view.

    How an email becomes an answer

    A small language model does exactly one job inside a pipeline of eight stages. The other seven are ordinary, testable code, because most of the work in understanding an email thread does not need a model — and the parts that do not need one should not depend on one.

    1. 1

      Parser

      Rebuilds the conversation from the uploaded .eml file(s). HTML is read as text, never rendered — a tracking pixel cannot fire.

    2. 2

      Security gate

      Every attachment is checked before anything opens it. File type comes from content, never a filename, so an executable renamed invoice.pdf is refused.

    3. 3

      Sandbox

      PDFs and Word files are read in a process with capped CPU and memory, no disk access, and a hard timeout — a process this app can afford to lose.

    4. 4

      Privacy

      Personal data is masked behind stable placeholders before anything is stored or shown to the model, and restored only for display.

    5. 5

      Enrichment

      Dates, open questions and who is waiting on whom are found by plain code, then handed to the model as ground truth — and shown to you directly, under "found by code, not by the model".

    6. 6

      The model

      Writes the summary and the suggested next step as strict JSON. It has no tools, no network access, and no way to act on anything it reads.

    7. 7

      Guardrails

      Every date, amount and address in the summary is checked against the source. Detected manipulation replaces the model's advice with a deterministic, safe one.

    8. 8

      Web app

      Shows the result — including the parts that did not check out, because the point is to be trustworthy, not to look clean.

    Why this is not just an API call

    The model is one stage of eight

    Dates, deadlines, participants, unanswered questions and how long a thread has waited are all found by ordinary code, then handed to the model as ground truth and shown to you directly. A deadline on screen is one a program found in the text.

    Nothing it says is taken on trust

    Every date, amount and address in the summary is checked against the source. Anything that cannot be traced back is shown as unverified, with the specifics.

    Attacks are detected and defused

    When an email tries to instruct the assistant, you are told, the model is warned before it reads, and the recommended action is replaced deterministically — because during evaluation the model described an attack correctly and then advised complying with it. Its action items are cleared too, so work planted by an attacker can never surface on the Tasks page stripped of the banner warning you not to trust it.

    Security, in short

    The full analysis, twenty threats and six things this deliberately does not defend against, is in the threat model.

    Nothing leaves the machine

    The model endpoint is loopback only, and a strict Content-Security-Policy stops the page loading any external script, font or image.

    A filename is never evidence

    Attachment types are detected from content. An executable named invoice.pdf is refused, not opened.

    Attachments run in a disposable process

    Near-empty environment, capped CPU and memory, no disk writes, killed if it overruns. Bytes arrive over a pipe — nothing touches disk.

    HTML is parsed, never rendered

    A tracking pixel cannot fire, so reading mail here never tells the sender you read it.

    Personal data is masked

    Masked before storage and before the model, restored only for display. A copied history database leaks nothing.

    The model has no way to act

    No tools, no network, nothing to call. The worst a successful injection achieves is a misleading summary — and the guardrails flag that too.

    Measured, not asserted

    15/15golden dataset cases, reproduced on two runs
    390tests, 97% line coverage
    ~18sper thread on an 8 GB M1, fully offline
    7 → 15eval score before and after the fixes it prompted

    Fifteen cases is a small dataset written by one person, so it measures the failures that were anticipated, not general accuracy. It earns its keep by catching regressions and by having found real bugs.

    Known limitations

    • The dataset is small and self-written — it catches regressions, not general accuracy.
    • A 4B model still drifts; the guardrails exist precisely because that is expected, not surprising.
    • Scanned documents and images are not read; those attachments are reported as unreadable.
    • Injection detection recognises known shapes — a novel phrasing may not be flagged.
    • 15–30 seconds per thread on an 8 GB M1. A larger model is more accurate and slower.
